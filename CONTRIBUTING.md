# Contributing

These rules come from the team's decisions (see `DECISIONS.md` and the GDD). `Q..` numbers point to the Questions tab of the shared doc.

## Setup

- Java 21, Gradle (use the wrapper: `./gradlew`).
- Any IDE. The `.editorconfig` sets indent and line endings; Spotless does the real formatting.
- Build: `./gradlew build`. Run tests: `./gradlew test`. Format: `./gradlew spotlessApply`.

## Workflow (no pull requests)

1. Create a branch from an up-to-date `main`: `type/short-name`, where type is `feature`, `fix`, `docs` or `test` (Q122). Examples: `feature/shop-roulette`, `fix/dash-cooldown`, `docs/uml-entities`, `test/bsp-invariants`.
2. Commit with Conventional Commits (Q123): `feat(shop): add roulette slot`, `fix(combat): clamp damage to 1`, also `test:`, `docs:`, `refactor:`.
3. Push the branch and wait for green CI.
4. Rebase the branch on `main`, wait for green CI again, then push the same commit to `main` (fast-forward only, linear history) (Q124, Q127).
5. Never force-push `main`. Never push a commit to `main` whose CI is not green.

## Definition of done (Q126)

- Code and tests (GDD 1.4.1 rules are written test-first: red, then green; Q121).
- Javadoc on every public class and method in `core` and `desktop` (Q105).
- draw.io UML updated (PlantUML is redone from the code after the build; Q108).
- CI is green.

## Code style

- Google Java Style, 100 columns, enforced by Spotless (Q87, Q88, Q92). Guidelines, not checked: methods about 30 lines, classes about 300 lines.
- Naming (Q90): no `I` prefix, no `Impl`. Interfaces get role names (`Renderer`, `LevelGenerator`); implementations say what they are (`XRayRenderer`, `BspLoopGenerator`); the pattern shows in the name where natural (`EnemyFactory`).
- English everywhere: code, comments, Javadoc, commits (Q91).
- No inline magic numbers (Q93). Tunable gameplay values go in JSON under `data/` (one file per category, snake_case). Code constants only for non-gameplay values (tick rate, tile size).
- A method that may find nothing returns `Optional`; constructors check inputs with `Objects.requireNonNull`; no annotation library (Q94).
- Unchecked exceptions for programming errors. Custom exceptions only where the caller can recover (for example `InvalidGameDataException`). Never catch and ignore (Q95).
- Logging with SLF4J (Logback backend). `System.out` is banned (Q96).
- Java records for value objects; final fields by default (Q97).
- Constructor injection by hand, one composition root in the launcher. No singletons: the event bus is passed in like any other dependency (Q103).
- Every Strategy, Observer and State role is an interface before any implementation (Q104).
- Mark patterns: a Javadoc line on every pattern class (for example `Pattern: Memento (originator)`) and an entry in `PATTERNS.md` (Q102).

## Architecture

- Modules: `core` (pure game logic, tested) and `desktop` (rendering, input, audio, LWJGL3 launcher) (Q98).
- Packages by feature: `combat`, `entity`, `item`, `level`, `ai`, `shop`, `debug`... (Q99).
- `core` may use libGDX math, collections and gdx-ai. An ArchUnit test bans graphics, audio, input and `Gdx.*` statics in `core` (Q100).
- Layered class hierarchy and passive items as Decorators: see GDD 1.3.1 (Q101).
- Debug features (R, F1, F2, F5 / TAB) are separate modules behind the `DebugFeature` interface. The engine never depends on them, and the game and its tests must pass with any of them disabled (GDD 1.1.2).
- Determinism: a seeded `RandomSource` and a fixed time step are injected. `Math.random()`, `new Random()` and `System.currentTimeMillis()` are banned in `core` (Q114).

## Tests

- JUnit 5 + jqwik (about 200 tries per property) + ArchUnit. No Mockito, no AssertJ: plain assertions and hand-written fakes that implement our interfaces (Q110, Q117).
- Names: `should_X_when_Y`, for example `should_deal_at_least_1_damage_when_resistance_is_high` (Q111).
- Structure: Given / When / Then in three blocks separated by blank lines; one behaviour per test (Q112).
- Location: `src/test/java` mirrors the main packages with one `<ClassName>Test` per class. Cross-class GDD 1.4.1 rules go in the `rules/` package, one class per section (`ShopRulesTest`, `CombatRulesTest`) (Q113).
- Test data: builders in code (`anEnemy().withHp(10).build()`); a few small JSON fixtures only for data-loading and hot-reload tests (Q116).
- Every bug fix starts with a failing regression test (Q115).
- Rendering: one test per renderer, render a frame and check the game state is unchanged. No pixel comparison (Q118).
- The full suite must run in under 30 s (Q120). JaCoCo fails CI below 70 % on `core` (desktop and the launcher are excluded) (Q119).

## CI (GitHub Actions, every push)

`spotlessCheck` -> build -> tests -> JaCoCo 70 % on `core` -> SpotBugs + PMD (Q125). Javadoc is generated by hand before delivery, not in CI (Q107).

## Assets and text

- Folders and names in snake_case, one folder per category: `assets/sprites/enemies/zombie_walk.png` (Q130).
- Every asset and its licence is listed in `CREDITS`.
- Plain Git for binaries. Switch to Git LFS only if music or large spritesheets arrive (Q132).
- No player-visible text in code, only keys with the format `area.element.detail`. `strings.properties` (EN, default) and `strings_fr.properties` (FR) must hold the same keys (Q131).

## UML

Design diagrams first in draw.io (GDD phase); after the build, redone in PlantUML from the code as built, as text files in `docs/uml` (Q108).
